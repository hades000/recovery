## M11 root cause

`main.tsx` renders `<App/>` in `<StrictMode>`. In development (the Playwright `webServer` is `npm run dev`),
React runs the `AuthCallback` effect twice. oidc-client-ts 3.5.0 `signinRedirectCallback` reads the stored
sign-in state with `removeState = true`, so the second call rejects ("No matching state found in storage").
Its `.catch` navigated to `/recovery`, while the first call navigated to `returnTo` (`/recovery/platform`).
The final URL depended on which promise settled last. The comment in `platform.spec.ts` blamed the mock
server for dropping the state; the app dropped it itself. The fix keeps the callback promise for the page
load (`signInCallback ??= userManager.signinRedirectCallback()`). The sign-in redirect leaves the app, so the
module is fresh each time the user returns.

## Assumptions (no question asked, L-RCV-03)

- A-01: A rollback is a decision under AGENTS 3.4 and uses decision code `AC-VERS`, with outcome `ROLLED_BACK`, until LOV-DECISION gets a rollback code (SU-02).
- A-02: `RWB_ENVIRONMENT` has no default in any profile. Local dev and CI-like local runs set it through `.env`. The Testcontainers ITs set `rwb.environment` in their `@SpringBootTest` properties (`ParameterConfigIT` already did; `RecoveryDatabaseIT` now does).
- A-03: The readiness detail for a database outage is status-only (`database: unavailable`), the same as the catalog endpoint's 503 status-only answer in TC-31/E7.
- A-04: `/infra/postgres/` is owned by the recovery tech leads only, pending ratification.
