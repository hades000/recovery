## 1. GAP-0165 (Register gap; ruling R-28590; sections: find it)
- Title: The access log is named by Architecture v5 but is not itemised in the Ownership Map
- Detail: Architecture v5 puts an access log in the rwb_access schema and gives the administration operation GET /admin/access-log, but the Ownership Map Tables sheet has no access log row, so the table name, its columns, its retention and its hash rule are not stated anywhere in this pack.
- Evidence: Architecture v5 slide 14, P4 DB line: 'schema rwb_access: Recovery roles as data, scope, masking policy, DoA table, access log'; slide 41; Ownership Map v1 Tables: role, permission, role_conflict, masking_rule, delegation_limit for P4, and no access log row.
- Proposed fix: The access log is read as a P4 table in rwb_access, append-only and created by the P4 DB story RWB-P4-E1039-DB; v5 names the owner and the read operation and leaves the definition to that story and to the Ownership Map.
- Owner role: ACE team

## 2. GAP-2069 (Register gap; ruling R-28592; sections: find it)
- Title: The access log has an API and an owner but no table in the Ownership Map
- Detail: The source puts the access log inside the decision log store. Version 3 places it in rwb_access (P4) with the API GET /admin/access-log, which the Ownership Map assigns to P4. The map holds no access_log table, so the store of the access log, its append-only mechanism and its chain are undocumented, although the source requires inserts only and a hash chain.
- Evidence: Source section 1 (access log 'inside the decision log store') and section 4 (inserts only); Ownership Map v1 Read me and Tables sheets have no access_log row; ownership.json api has 'GET /admin/access-log' with owner P4 and no table entry.
- Proposed fix: The access log is an append-only table in rwb_access (P4) behind GET /admin/access-log; the DB story of P4 creates it and the contract story publishes the read path.
- Owner role: Service owner P4 rwb-access

## 3. GAP-2340 (Register gap; ruling R-28593; sections: find it)
- Title: The capability-area code, the result code and the field list of a document content read in an access entry are not specified
- Detail: An access entry states a capability area, a right and a result, and for a case read it also lists the field IDs returned with their masking position. For a document content read the API declares the capability as Documents with right R, but no source gives the exact area code string an entry carries (DOCUMENTS, DOCUMENT or the document hub module code), the result value of a served read, or whether a content read (which returns a binary body and no field values) lists any field ID at all. AC1 and AC6 of this story need those three answers to state a record the central ledger and the access log ...
- Evidence: Legacy RWB-E1-039 AC9: 'area PLATFORM_ADMINISTRATION, right R and no case ID'; AC1: 'its actions list the field IDs returned, with DF-PTY-007 and DF-PTY-016 marked masked'; TSD P5 v2 API-P5-004: 'Authorization Documents, right R, scope applied' and 'Response Binary'; RWB-P4-E1039-CON 11 gives capabi ...
- Proposed fix: Add the capability-area code list that includes the document hub, the result code list and the rule for a read with no field values to the reference data or to RWB-P4-E1039-CON; until then the area is DOCUMENTS, the result is the legacy success value and a content read lists no field ID.
- Owner role: Data steward

## 4. GAP-2342 (Register gap; ruling R-28594; sections: find it)
- Title: The incident queue name and the session-answer reuse bound of the content read are not specified
- Detail: The legacy story raises an incident to the platform administrator queue when the access entry cannot be written, and this story repeats that path when the record fails. No source names that queue in the target, gives the reuse bound of the cached session answer that carries the grant, or states whether the raise goes through the parameters-driven incident route of the platform. Two configuration values therefore have no source, and the exception path of AC2 and X8 depends on both.
- Evidence: Legacy RWB-E1-039 X1: 'the read or export returns no data; status 503; an incident is raised'; AC7: 'the system raises an incident to the platform administrator queue'; no queue name, reuse bound or parameter key appears in TSD P5 v2 or in RWB-P4-E1039-CON.
- Proposed fix: Name the incident queue and the reuse bound in the platform observability and parameters baseline, and record them as parameter rows; until then the queue is a parameter of this service and the session answer is reused within one request only.
- Owner role: DevOps team
