- Proposed fix: The attempt counter and the exception rule R-UNI-34 are named as the message capability's own send attempt, counted once per relay window, and the path's internal retries are excluded from the count; the platform relay owner confirms the window semantics.
- Owner role: Solution architect

## 3. GAP-1072 (Register gap; ruling R-22580; sections: find it)
- Title: How the LINE OA read status reaches rwb-comms is not specified
- Detail: The legacy requires a second status for the same send: LINE OA reports delivered and then read, and the interaction ends at delivery status READ. Nothing in the sources says whether that second status arrives as a callback from the ACE notification path into rwb-comms, as a poll of the path, or as a batch result, and the legacy interface names only MessageResultListener.onResult with no transport.
- Evidence: legacy section 4 step 7: 'the ACE notification path: returns the delivery result (NSS result code; LINE delivered and read)'; legacy section 13 configuration: 'LINE OA status map to DELIVERED, READ (data steward)'; no transport named in TSD P6 T5.1
- Proposed fix: The ACE notification path owner states the result transport for both channels; rwb-comms accepts either a callback or a poll as a result for a known external reference, and a result for an unknown reference is not applied.
- Owner role: Solution architect
