## 1. GAP-1739 (Register gap; ruling R-23424; sections: find it)
- Title: legal_action.case_id is a uuid in the FSD, while ADR-014 and DP-01 forbid a cross-schema foreign key and require a varchar(255) business key
- Detail: Every field catalog of the FSD types legal_action.case_id as uuid with the meaning 'The recovery_case this record belongs to' and the required flag Yes, and lists no foreign key. Under Architecture v5 the case lives in schema rwb_case and this service writes only schema rwb_litigation, so a uuid column carrying a cross-schema reference is exactly what DP-01 forbids; the platform pattern is a business-key column of type varchar(255) with no foreign key. The same column is the key of almost every entity in this schema, so the DB story cannot start until it is settled.
- Evidence: FSD S4 A2.6.3.2 to A2.21.3.2 field catalog row 'legal_action.case_id / The recovery_case this record belongs to / uuid / Yes / None / No'. Recovery Workbench Architecture v5 Text Extract v1 slide 20 (schema and login per service) and slide 45. Recovery Workbench Microservice Story Template and Rules ...
- Proposed fix: Use a business-key column of type varchar(255) with no foreign key, keeping the FSD's field name; the case number is the business key and no identifier of another schema is stored as a foreign key.
- Owner role: Data architect
