X1. Statuses and transitions. Every status in §9, the business rules and the ACs is a value of LOV-CASE-STATUS (Reference Data v5,

X2. Decisions. Every business rule, AC and constraint is checked against the decisions taken in Decision Log v11 (D-RCV-nn and

X3. Fields. Every column named in §4, §8, §11, §13 (index, constraint and migration lines) and the ACs exists in LDM v9 Fields with
    the same table, name, type, length and nullability, and the story uses it with the meaning in the Description column. A
    renamed column (for example a name the ACE mapping or ACE Data Tier Map v1 §5 replaced) is Outdated.
X4. Lists and parameters. Every LOV-* and parameter key exists in Reference Data v5 or parameter-catalog.csv, with the same owner
    route (Lists sheet: "list read, RWB-P3-E1043-CON" against "parameters contract, RWB-P3-E1042-CON"). The same parameter written

X5. Contracts. Every REST operation in §12.1 and §12.2 exists in the owner's yaml in API Specification v5 with the same path,

    DP table of §13 exists as a file under 04 User stories/Recovery Workbench Service Story Files v1/.
X6. Events, workflows and schedules. Every event in §12.3 and §12.4 matches Kafka Catalog v1 (type name, topic, key, payload,

    schedule in §12.6 matches Batch and Scheduling Design v5 (configured or "not configured").
X7. Rule IDs. Every R-* rule cited in §8 has the same meaning in Business Rules v4, Rules. Every literal rule ID in an AC or a fake

X8. Messages. Every MSG-* in §5, §12 and §14 matches Error and Message Standard v4 in English text, placeholders and meaning

X9. Test cases. Every TC ID in §16 is a row of Test Cases v8, Story test cases; its Given, When and Then values match the AC it

    personal data is carried, is a Conflict.
