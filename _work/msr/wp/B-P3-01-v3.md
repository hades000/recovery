A story fails a check when a value in the story differs from the authoritative source, when two authoritative sources differ from
each other on a value the story uses, or when two parts of the same story (or the story and a sibling) contradict each other.
For every failure write one gap row (format §R9; type Conflict, Outdated, ID collision, Missing or Ambiguous) whose "evidence"
quotes both sides with document, version and sheet and row (or section), and whose "proposed" names the winning document by the
precedence: (1) D-RCV-60 realignment and Architecture v5, with the catalogs above; (2) D-RCV-36, D-RCV-35 and ADR-010, 14 Story
Updates; (3) all other documents. A precedence-3 document that predates D-RCV-60 and conflicts with it is Outdated against that
document. Never decide a business value: when the sources do not settle it, type Ambiguous, owner role Product owner or Business
analyst, and one assumption row.
Document checks
X1. Statuses and transitions. Every status in §9, the business rules and the ACs is a value of LOV-CASE-STATUS (Reference Data v5,
    Values) with the same code and case, and every transition is a row of Case and Workflow Model v6, Status transitions, with the
    same event. A status-class word (for example "Active" in the Case status sheet's last column) used as a status is a Conflict.
    A new value an AC adds to a closed list (Reference Data v5, Lists "Closed list") is a Conflict with the list type.
X2. Decisions. Every business rule, AC and constraint is checked against the decisions taken in Decision Log v11 (D-RCV-nn and
    taken DL items). A rule that differs is a Conflict citing the decision ID. Every open DL item the story depends on (for
    example DL15, DL16, DL17, DL43) needs an assumption row that states the recommended option; when none exists in either register,
    write the gap (type Ambiguous) and the assumption row.
X3. Fields. Every column named in §4, §8, §11, §13 (index, constraint and migration lines) and the ACs exists in LDM v9 Fields with
    the same table, name, type, length and nullability, and the story uses it with the meaning in the Description column. A
    renamed column (for example a name the ACE mapping or ACE Data Tier Map v1 §5 replaced) is Outdated. A field ID range mapped to
    a table other than the one the dictionary gives is a Conflict. A source field in the ACE Field Gap List is named in the row.
X4. Lists and parameters. Every LOV-* and parameter key exists in Reference Data v5 or parameter-catalog.csv, with the same owner
    route (Lists sheet: "list read, RWB-P3-E1043-CON" against "parameters contract, RWB-P3-E1042-CON"). The same parameter written
    under two names in the story, the catalog or either register is an ID collision. A key absent from parameter-catalog.csv is
    Missing; an empty catalog file is one Missing row for the WP (not one per key), cited by every story that needs a key.
X5. Contracts. Every REST operation in §12.1 and §12.2 exists in the owner's yaml in API Specification v5 with the same path,
    parameters, enums and error schema, and the provider-consumer pair is a row of the Service Contract Catalog v1. A field the
    yaml holds as a closed enum while the story treats it as list data is a Conflict. Every HTTP status the story maps has a message
    ID. Every story key in the metadata table and the DP table of §13 exists as a file under
    04 User stories/Recovery Workbench Service Story Files v1/.
X6. Events, workflows and schedules. Every event in §12.3 and §12.4 matches Kafka Catalog v1 (type name, topic, key, payload,
    consumers). Every workflow and activity in §12.5 matches Temporal Catalog v1 (name, task queue, cross-queue call). For EVERY
    workflow state its workflow ID form and its start rule (start, signalWithStart, duplicate-start policy) and check them against
    Temporal Catalog v1 Workflows and Platform rules and Workflow Engine Design v4; a form that differs or is "not specified" is a row
    even when an architecture-level gap exists (name it as related). Every schedule in §12.6 matches Batch and Scheduling Design v5
    (configured or "not configured", catch-up window, overlap policy).
X7. Rule IDs. Every R-* rule cited in §8 has the same meaning in Business Rules v4, Rules. Every literal rule ID in an AC or a fake
    (for example EXCL-004) exists in a current source, not only in a legacy story copy. A rule the flow applies with no ID is Missing.
X8. Messages. Every MSG-* in §5, §12 and §14 matches Error and Message Standard v4 in English text, placeholders and meaning
    (the "When" column), and no story assigns a new meaning to an ID the standard already uses (ID collision).
X9. Test cases. Every TC ID in §16 is a row of Test Cases v8, Story test cases; its Given, When and Then values match the AC it
    covers; and the requirement it traces to has the TC in RTM v7. A TC listed with no AC of this story, and an AC with no TC, are
    Missing. New TC IDs of a CON, DB, INF or OPS story that are not yet in Test Cases v8: one P3 Missing row per story.
X10. Personal data. Every key or field in an event payload, a workflow payload, a log line or a "no personal data" guardrail is
    checked against Data Classification v5. A field classed "Indirect identifier" or higher, carried where the story says no
    personal data is carried, is a Conflict. An output "masked by role" needs a masking rule in a source; none is Missing.
X11. Platform names. Every Java package segment is not a Java reserved word (abstract assert boolean break byte case catch char
    class const continue default do double else enum extends final finally float for goto if implements import instanceof int
    interface long native new package private protected public return short static strictfp super switch synchronized this throw
    throws transient try void volatile while true false null); a reserved word is a Conflict, severity P1, owner role Solution
    architect. Flyway file names follow the Service Template Specification v1 convention.
X12. Source access. In a story that is not owned by P1 rwb-source-data, every Given, test data line or flow step that names
    recovery.v_ace_*, v_ace_*, account_ext or party_ext is Outdated (DP-05; ADR-010). Legacy markers JOB-nn, "decision log",
    "job record" and COLLINS in an AC or TC line of a story whose §12.5 names a workflow are Outdated (DP-03, DP-10).
Behaviour and design checks
X13. Inner consistency. Each business rule's outcome in the cited source (for example R-UNI-39 "Block the action and raise an
    incident") appears in the exception path and the AC that cover it; an outcome the AC leaves out is a Conflict. The order of
    writes in §4 matches §13 (components and build steps). Each §5 row's "Covered by" AC actually sets up that row's trigger; an AC
    that does not is Missing. A value drawn outside the transaction that §4 says rolls back (for example a database sequence) is
    Ambiguous unless the story states that gaps are allowed. A period word ("entry year", "business date", "daily") with no
    defined source or time zone is Ambiguous.
X14. Scale. Take the volume the story serves from the PRD non-functional table, NFS v4 and Volume and Scale Forecast v4, and work
    out the calls per run and the workflow events per run from §4 and §12. Compare with the Temporal Catalog v1 Platform rules
    (history event and size limits, Continue-As-New rule), the run window in Batch and Scheduling Design v5 and the timeout in
    §12.2. A run that cannot fit is a Conflict; a story with no paging, chunking or Continue-As-New rule for a run over the limit is
    Missing. Show the arithmetic in "evidence". Every NFR with a numeric target that applies to the story's capability and has no
    AC or named NFR story is Missing.
X15. Resilience and caching. Every consumed call and handler is checked against Error Handling and Resilience Standard v4
    (timeout, retry, circuit breaker, bulkhead, activity retry policy, non-retryable errors, failure behaviour). A story value that
    overrides the standard, or an exception path whose outcome ignores the activity retry policy, is a Conflict. Every cache the
    story keeps (permissions, rule models, reference data) is checked against Security and Access Design v5 and Rules Engine Design
    v4 (refresh events, lifetime, behaviour when the owner is down); a missing refresh event or a cache-drop where the design says
    keep-last-good-and-swap is a Conflict. An open question in 19 Jira Open Questions on the same behaviour is named in the row.
X16. Requirements. Every REQ-* and FR-* in the header and §18 exists in the BRD or PRD with the same meaning and is covered by an AC
    or a flow step of this story; one that the story does not build (or puts out of scope in §19) is a Conflict. An FR ID used twice
    in the PRD with two meanings is an ID collision. A PRD requirement on the story's capability that no story of the WP covers is
    Missing. The RTM test list that differs from §18 is already X9.
X17. Screens. Every SCR-* in §15 exists in Screen Specifications v1.md with the states empty, loading, error and no access; a missing
    state or a field bound straight to another service's table is a row (Outdated when the screen spec predates D-RCV-60).
X18. Ownership split. Every AC cited in §5 or §7 but owned by another story (integration, sibling) exists there in Given/When/Then
    with the same values; one that does not is Missing. An AC that asserts a write made by another service (for example an access
    event written by rwb-access) is a Conflict with the owner. The same operation, event, payload or field defined in the APP, CON,
    OPS, ITG and sibling stories must agree; a difference is a Conflict naming both stories.
X19. Register currency. Every GAP-nnnn and ASM-nnnn the story cites exists with the same text. A cited gap that a current source
    already answers (for example a login name now fixed in a TSD) is Outdated. Every open register gap whose description names the
    story, its legacy key or an object the story uses, and that the story does not cite, is listed in report R3 (no gap row).
X20. Versions. Every document version the story cites that is not the highest in Document Index v14 is one P3 Outdated row per
    story (all versions in one row).

Assumptions. An assumption row may adopt only a value or option that a source already writes (for example the recommended option of

value, the assumption is "built as written in the story until <owner role> rules", with confidence Low.
