- Slice choice: the legacy key is one placement command, and the plan gives it four application slices on four services with no legacy criterion on this one. The rwb-deviation slice is therefore the one fact the interface has to obey and no other service can supply — the hold an open deviation puts on a case, carried on `DeviationRaised` (EV-06) and `DeviationCleared` (EV-07) with the exact open count, the handler and the return point — while the refusal itself stays with rwb-case (`RWB-P3-E2036-APP`) and the caller-facing admission with rwb-integration (`RWB-P2-E2036-CON` and `-APP`).
- The main finding of this key for S8: the hold has no published element set. The two events are named by TSD S8 T5.3 and the topic by the naming rule, but no source publishes an AsyncAPI document or a property set, and the case side that sets and clears `recovery_case.deviation_open` (DF-CAS-019) publishes no event and no operation either. The hand-over is an event contract that neither side publishes in full, so it is recorded as one combined gap and carried with placeholders (GAP-3102; ASM-5316, ASM-5317).
- The second finding: the count is the safeguard. A case may hold more than one open deviation and resumes only when all are cleared (FEAT-DVH-09; FSD S8 A2.9), so a per-deviation flag would release a case that is still disputed and the interface would place it. The count is read inside the transaction of the raise and of the clear from the rows whose `cleared_at` is empty, and no counter column is added (ASM-5318); the one migration is a non-unique partial index, because a unique index on the open rows of a case would refuse the second raise (ASM-5327).
