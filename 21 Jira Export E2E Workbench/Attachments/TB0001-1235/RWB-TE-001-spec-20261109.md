## User story intent interpretation

As a squad member (RW-TRIBE), I want the recovery module folder and packages in the ACE repository with a build-time boundary test, so that no module calls the inside of another module and no recovery code calls a system of record directly.

The story is a repository-skeleton enabler. It creates one Spring Modulith application module `recovery` with 19 nested modules, each with a published `api` part and an `internal` part, writes the module map that names them, and adds JUnit/ArchUnit tests and an ESLint rule that make the existing build fail on a boundary violation. It ships no runtime code: `RecoveryAccessGuard` moves to RWB-E1-022 (D-RCV-36). Every later Epic 1 story builds inside this skeleton. A violation is a failed merge request, not a production defect. The measure is boundary violations merged to the default branch, target zero.

- No runtime code, no new endpoint, no pipeline change.
