A2. When do the jobs run?
-------------------------
All jobs run on Quartz in the ACE service. Times are Asia/Bangkok.

  JOB-09 File loads
    - Weekly on Monday at 04:00: CCMS, SVAF, RPS and WIN.
    - Monthly on the 2nd working day: AMIS and GL.
    - Starts when the file arrives. The file must match the file pattern in
      the interface setup.
    - If no file is there by the cut-off, the run is marked MISSING.
    - Owner: Data steward.

  JOB-10 WIN outbound notices
    - Every day at 16:00, using the notices approved by P6.
    - Owner: Platform administrator.

  JOB-11 Outbox sender
    - Every minute. No dependency.
    - Picks up items that are waiting (PENDING or RETRY) and due now.
    - Owner: Platform administrator.


A3. How do the jobs work, and what do they depend on?
-----------------------------------------------------
JOB-09 (files coming in)
  1. Find the file in the inbound folder.
  2. Write a run record with status RECEIVED (file name, hash, date).
  3. Run four file checks (see Part D). The old data stays if any check fails.
  4. If all pass, hand the records to the owning module loader and mark the
     run LOADED.
  5. The loader (not this job) publishes LoadCompleted (EV-26) or
     LoadRefused (EV-27).

JOB-10 (queue the notice file)
  1. Receive the approved notices from P6.
  2. Write one outbound item for the day's file, inside the caller
     transaction. The duplicate guard is "INT-14:" plus the business date, so
     a second run for the same date adds nothing.

JOB-11 (send the file)
  1. Pick due items with a lock, so two threads never send the same item.
  2. Send over SFTP (only SftpTransport may open SFTP). Mark SENT.
  3. Mark ACKNOWLEDGED when the acknowledgment file arrives.
  4. If still SENT with no acknowledgment after 30 minutes, send again. This
     30 minutes is an assumption (see decision DL11).

Dependencies
  - JOB-09 needs: the file; the E1-007 tables and adapter; the owning module
    loader (E1-004, E1-009 and later loads); the check rows DQ-057 onwards.
  - JOB-10 needs: approved notices from P6; E1-007 OutboundFiles; WIN notice
    wording (RWB-E2-021).
  - JOB-11 needs: items from JOB-10 or any other outbound request; SftpTransport;
    the INT-14 outbound path from Henka (A7).
  - RWB-E1-007 itself depends only on RWB-E1-001 (the database schema). The new
    Data Loading story depends on E1-007, not the other way round.


A4. Input, output and business rules
------------------------------------
JOB-09
  Input: the file for the interface.
  Output: one run record per file, and records passed to the owning module.
  Rules:
    - Reject the whole file if a check fails.
    - Keep unknown references in an exception list (loader).
    - Same file again (same hash) is marked DUPLICATE and nothing loads.
    - Keep the previous load if a file is rejected or missing.
    - Mark the data product stale one business day after the file was due.

JOB-10
  Input: approved notices (contract number, addressee, address, notice type,
  template version, document reference). About 1,900 letters a month.
  Output: one outbound item for the day's file.
  Rule: hold the case step until the file is acknowledged.

JOB-11
  Input: waiting items that are due.
  Output: the SFTP transfer and the item status.
  Rules:
    - The number of attempts and the waits come from the interface setup,
      not from code. INT-14 has 3 attempts and waits of 5, 15 and 45 minutes.
    - One send per item, even with two threads.
    - Outbound items carry case IDs only, never names or addresses.


A5. Errors and expected results
-------------------------------
The full answer is in Part C. In short:
  - Rejected file: run marked REFUSED, message MSG-P1-002, old data stays.
  - Missing file: run marked MISSING, product stale one business day later,
    message MSG-P1-001.
  - Send failed: case goes to RETRY_QUEUE; after the last try the item is
    EXCEPTION, the cases go to EXCEPTION_QUEUE, a task goes to RW-PLATADM and
    MSG-P2-001 is logged.
  - Resend: item goes back to PENDING with count 0; response MSG-GEN-005.

How messages are sent in this design
- Internal alerts use the ACE notification path. The design lists the channel

- The application log gets the message ID and the check ID. Check IDs and codes

- The screen for loads and files is SCR-44. It is built in Epic 2 and fully in
  Epic 8. There is no screen for these jobs in Epic 1.
- In Epic 1 the run status can be read with GET /admin/jobs (Platform
  administration, read). Whether it lists the file runs of this story is TO
  CONFIRM.

CASE 1 - AC2: a file fails a check (for example a control total mismatch)
  The CCMS file CCMS_COLL_20261109.txt has 4,200 records but the last line says
  4,201. The whole file is rejected.
  Message MSG-P1-002: "The CCMS load for 2026-11-09 was refused: control total.
  The previous load is still in use."
  API response: No. The job has no caller.
  How it is communicated:
    - Alert through the ACE notification path (Workbench and email, TO CONFIRM).
    - Run record shows REFUSED, the failed check (DQ-059) and no records passed.
    - The message ID and check ID go to the log. File contents are never logged.
    - LoadRefused (EV-27) is sent by the loader.
    - The old load of 2026-11-02 stays in use.
  Who is told: the data steward group, as the AC says. The COLLINS rejection
  flows also tell the platform administrator group. Is the platform
  administrator also told here? (TO CONFIRM.) The data steward asks the sending
  team for a new file by hand. The system sends nothing to the sending team.

CASE 2 - AC3: retry limit reached
  The WIN file WIN_NOTICE_20261110.txt (85 notices on 85 cases) fails to send on
  attempts 1, 2 and 3.
  Message MSG-P2-001: "{item} was not delivered to {interface} after {count}
  attempts. It is in the exception queue."
  API response: No. The message is not returned by an API. The item is read with
  GET /admin/outbound-items (Platform administration, read; filters on status
  and interface). It shows status, attempt count, last error, case count and
  owner role, but no message code.
  How it is communicated:
    - The message goes to the log on the last failed attempt.
    - A task is created for the owner role (RW-PLATADM for INT-14).
    - After attempt 1 each of the 85 cases moves to RETRY_QUEUE. After attempt 3
      each case moves to EXCEPTION_QUEUE.
    - SCR-44 will list outbound items (Epic 2 and Epic 8). Its message list does
      not yet include MSG-P2-001.
    - No email is specified for this message (TO CONFIRM).
  Who is told: the platform administrator, through the task. Case owners see the
  case status change. The target for alerts is 15 minutes (NFR-068, proposed).

CASE 3 - AC5: file missing at the cut-off
  No SVAF file for 2026-11-09 is in the inbound folder by Monday 04:00. On
  2026-11-10 the SVAF data product is marked stale.
  Message MSG-P1-001: "{product} is from {date}. Today's load has not arrived."
  API response: No. The job has no caller.
  How it is communicated:
    - Run record for INT-11 shows MISSING. No loader is called.
    - On 2026-11-10 (one business day after the due date) the freshness check
      marks the SVAF product (DP06) stale.
    - A warning with the age of the data shows on the screens that use it.
    - The data steward group gets MSG-P1-001 from the freshness check.
    - The previous appraisals stay in use.
  Who is told: the data steward group (alert). Screen users see the warning. The
  data steward asks the sending team for the file by hand.
  Open: is the alert an email, a Workbench notification, or both?

CASE 4 - AC9: resend from the exception queue
  Outbound item OB-0002 is in EXCEPTION after 3 attempts. A platform
  administrator resends it. The item goes back to PENDING with attempt count 0.
  Message MSG-GEN-005: "Saved."
  API response: Yes. POST /admin/outbound-items/{itemId}/resend (Platform
  administration, update), with an If-Match version.
    Success: 200 with the item (status PENDING, attempt count 0).
    Errors (problem+json with message code and Thai text):
      401  MSG-P4-001   no valid session or role
      403  MSG-P4-002   caller may not do this (for example a case owner)
      404  MSG-P4-003   item not found or out of scope
      409  MSG-GEN-004  the version is old
      503  MSG-GEN-006  service unavailable
  How it is communicated:
    - The resend is written to the ACE audit log with the user and the time.
    - The message ID goes to the application log.
    - The message shows from the response of the call (SCR-44 from Epic 2).
      SCR-44 does not yet list MSG-GEN-005.
  Who is told: the platform administrator who made the call. The audit entry is
  kept for audit. Nobody else is notified.
  Gaps in the API:
    - The item response has no message field, so "the response carries
      MSG-GEN-005" cannot be met as the contract is written. PROPOSAL: add a
      message code to the 200 response, or change the AC to say the screen shows
      MSG-GEN-005 after a 200.
    - "Saved." does not say the item is queued again. The message standard asks
      a confirmation to say what happened and what follows. A resend message of
      its own would follow the standard (PROPOSAL).
    - A resend on an item that is not in EXCEPTION has no defined 409 message
      (TO CONFIRM).

1. WHAT FILECHECKRUNNER DOES
----------------------------
FileCheckRunner is a small checker. When a file arrives, it checks the file
BEFORE any record is used. If every check passes, the records are passed on to
be loaded. If any check fails, the whole file is rejected and nothing is loaded.
The old data stays in use.

It makes four checks:

  Check            What it looks at
  ---------------  -------------------------------------------------------
  Business date    Is this file for the right date, and is it new?
  Structure        Are all the columns there, with the right type and size?
  Control total    Do the record count and the total amount match the last
                   line (trailer) of the file?
  Keys             Does every record have its key, and is each key used only
                   once?

Notes on your diagram
- The label "DQ01" is a different thing. DQ01 is a data quality rule in another
  story (E1-006). The file checks have names like DQ-058 (with a hyphen). For
  the CCMS file they are DQ-057 to DQ-060. Please change the label.
- The first field in the diagram (DF_COL_001) is an ID the Workbench creates
  itself. It is not a column in the file. The checker only checks columns that
  are really in the file.

Not done by FileCheckRunner (other stories do these)
- Checking that an account or customer exists (References).
- Checking that a code is in the list of values.
- Checking that the file is not too different from last time (Movement).

4. THE RULES
------------
Rule for all checks: no tolerance. One fault rejects the whole file.

4.1 Business date
  - The date in the first line of the file must be the date we expect. For a
    weekly file this is the Monday the file is due (the date in the file name).
  - A file for a date that has already been loaded is rejected, even if the
    content is different.
  - The same file sent twice is not a failed check. It is marked DUPLICATE and
    nothing is loaded again.

4.2 Structure
  - Every expected column is in the first row of the file. None missing, none
    extra.
  - Every record has the same number of columns.
  - Every value matches its type: an amount has digits and at most 2 decimals,
    a date is a real date.
  - Every value fits the size of its field.
  - A Required field is not empty. (Our proposal. Please confirm.)

4.3 Control total
  - The number of records equals the record count on the last line.
  - The sum of the amount column equals the total on the last line. Exact
    sum, to 2 decimals, no rounding.
  - A file without an amount column is compared on record count only.
  - A file with no last line, or an unreadable one, fails this check.

4.4 Keys
  - The key field is filled in every record.
  - No key value appears twice in the file.

Where the numbers come from
- Dates, totals, field lists and keys come from the file and from data tables.
  Nothing is written in the program code.

Privacy
- The file contents are never written to the log. Only the file name, the
  counts, the line number, the field name and the check result are logged.


5. WHAT HAPPENS (EXPECTED RESULTS)
----------------------------------
If every check passes
  - The records go to the loader.
  - The run is marked LOADED with the record count.

If any check fails
  - The whole file is rejected. The run is marked REFUSED.
  - The run record shows which check failed.
  - No record goes to the loader.
  - The previous load stays in use.
  - The message MSG-P1-002 is used: "The {source} load for {date} was refused:
    {check}. The previous load is still in use." The {check} is "business
    date", "structure", "control total" or "keys".
  - The alert, the stale marker and the events are done by the job and the
    loader (new Data Loading story).

  Case                                         Failed check   Run status  Records loaded
  -------------------------------------------  -------------  ----------  --------------
  Good file                                    none           LOADED      all
  Wrong date in the first line                 business date  REFUSED     0
  Date already loaded, content different       business date  REFUSED     0
  Same file sent again                         none run       DUPLICATE   0
  A column is missing                          structure      REFUSED     0
  Letters in an amount, or an impossible date  structure      REFUSED     0
  Value longer than its field                  structure      REFUSED     0
  Required field empty                         structure      REFUSED     0
  Record count differs from the last line      control total  REFUSED     0
  Amount total differs from the last line      control total  REFUSED     0
  Key empty                                    keys           REFUSED     0
  Key used twice                               keys           REFUSED     0
  No file by the cut-off                       (job, not      MISSING     0
                                               this checker)

Example from the story: the CCMS file CCMS_COLL_20261109.txt has 4,200 records
but the last line says 4,201. The control total check fails (DQ-059), nothing
is loaded, and the load of 2026-11-02 stays in use.

If a file has more than one fault, all results are saved. The first fault in
the order above is shown in the message.
