## User story intent interpretation

As a platform administrator (RW-PLATADM), I want every recovery schema change applied by a versioned
Flyway migration, one per story, forward-only in production, with the schema name taken from a
parameter, so that the database in every environment is the sum of known migrations and nothing else.

The story is an engineering enabler. It gives every later recovery story one way to change schema
`recovery`: a numbered, checksummed file in `db/modulemigration/recovery/`, applied by the recovery
module's own Flyway bean and history table, checked by a lint in every build. It ships **no production
migration file**; the first real file comes from RWB-E1-042 (`V0001`) and the table baseline from
RWB-E1-001 (`V0003`) under the merge-order map (D-RCV-34).

## Status-transition matrix

No case status changes. Migration state per version in `flyway_schema_history_recovery`:

| From | Event | Condition | To | Side effects |
|---|---|---|---|---|
| Pending (file on classpath, no row) | Recovery migrate | All statements succeed | Applied | Row with checksum, `success=true`. |
| Pending | Recovery migrate | A statement fails | Pending (unchanged) | Transaction rolled back; no row; run fails (app start fails / job exits non-zero); no automatic retry. |
| Applied | Recovery migrate | Checksum matches | Applied | Nothing applied. |
| Applied | Recovery migrate | Checksum differs / file missing | Applied (unchanged) | Validation fails; run fails; nothing applied. |
| Applied (newer than the running tag) | Older tag runs recovery migrate | Version is "future" | Applied | Ignored (`*:future`), run succeeds (SPEC-014). |
