### 1. Story

As a **litigation officer (RW-LITOFF)**, I want **every document `rwb-document` generates or regenerates to be stamped with the one Legal-approved template version it came from and to carry only merge values the catalog in force knows**, so that **a letter on a case can always be traced to the approved wording it used, and a template change never silently alters a document already issued**.

Inside `rwb-document` this is the document-side binding of the catalog, not the catalog itself:

- Service `rwb-document`, schema `rwb_document`, REST base `/api/recovery/document/v1`, topic `rwb.document.events.v1`, Temporal task queue `rwb-document` in namespace `rwb-recovery`, Java package `th.co.scb.ace.workbench.recovery.document`.
- **This is the secondary P5 slice of RWB-E1-046 and it owns no legacy acceptance criterion.** Legacy AC1 to AC8 stay where the split puts them: RWB-P6-E1046-APP carries the version numbering, the approval columns, the merge code check, the field-ID check, the repeat load and the current-version selection, and RWB-ITG-E1046-ITG carries the composed proof. The nine criteria of section 7 are new under D-RCV-60 and test only the P5 binding.
- **The catalog stays with its owner.** `template` and `merge_field` are P6's tables in `rwb_comms` (ownership map; RWB-P6-E1046-CON 12.7). This service creates neither, copies neither and never reads `rwb_comms` by SQL: it asks the catalog contract for the version in force and for its merge field list, one hop, 2 s timeout (DP01, DP11).
- **The local facts are `document.template_id` and `document_field`.** `document.template_id` (DF-DOC-032) holds the identifier of the catalog version the document was generated under, and each merge value is written as a `document_field` row whose `field_name` (DF-DOC-014) is a merge code of that catalog version. The legacy relationship "`document.template_id` many to 0 or 1 `template`" (TSD P5 v2 T3.3) becomes a soft reference across services with no foreign key and no cross-schema join.
- **Three operations of the service run the binding step** — `POST /cases/{caseId}/generated-documents` (API-P5-016), `POST /documents/{documentId}/regenerate` (API-P5-017) and `PATCH /documents/{documentId}/fields/{fieldId}` (API-P5-006). This story adds no endpoint; it supplies `TemplateVersionBinder`, `MergeValueBinder` and `CatalogCurrentVersionClient`, which those operations call (12.1).
- **No event is published and none is consumed.** The service's two events, `rwb.document.DocumentStored.v1` and `rwb.document.DocumentFieldsExtracted.v1`, belong to RWB-P5-E1024-APP and RWB-P5-E1053-APP; DP-09 is not a pattern of this story and the stamp is not announced.
- The reference lists are read as data through the rwb-case reference-data contract (DP07); the base is the owner's base (DP13); the index the binding needs is one step in the per-service Flyway sequence (DP15); the screen path is the gateway-bff composite route (DP19).
- The database login is one per service (DP02) and its name is Not specified in the source documents (GAP-2343; ASM-3897); this story says "the rwb-document login".

### 2. Business rationale

Legacy RWB-E1-046 makes the wording of a notice a data release: Legal approves a template version, and generation may use only a version that is Approved and may fill only fields the catalog knows. The P6 slice builds that catalog. This slice answers the other half of the same control: the document that was actually produced must carry the version it used, and the values inside it must be values the catalog allowed (CTL-14; REQ-OCC-002). Without it, an approved version could be replaced after a letter was issued and nothing on the case would show which wording was sent.

The realignment changes the mechanics, not the rule:

1. **One schema, one base.** `rwb_document` replaces the recovery schema and `/api/recovery/document/v1` replaces the monolith base (DP01, DP13). No `recovery.*` table and no `rwb_comms` table is named by a statement of this service.
2. **The catalog is a contract, not a table.** The in-process `TemplateCatalog` interface becomes the `rwb-comms` catalog contract (DP11), with a fake from Day 1, so the P5 binding builds before P6 is ready. A refusal from the catalog is carried to the caller unchanged: MSG-P6-005 for a version with no Legal approval, MSG-P6-003 for a withdrawn version, MSG-P6-006 for a merge code outside the catalog.
3. **The stamp is an identifier, not a copy.** The document holds `template_id` only. The code, language, approval user, approval date, body and valid-from of the version stay with their owner and are read when they are needed; no denormalized template attribute is written into `rwb_document` (BR3).
4. **Merge values become document fields.** A merge value is a `document_field` row with the merge code as its name, so the document index, the PATCH of one field and the extraction index answer the same rows (RWB-P5-E1024-APP, RWB-P5-E1053-APP). A code marked `personalData` is masked by role on every read and never logged (Guardrails).
5. **A regenerate is a new version under a new stamp.** The earlier version keeps the stamp it was issued under; the new one carries `previous_version_id`, the catalog version in force at the regenerate and its reason (API-P5-017; BR4).

It serves REQ-OCC-001 by holding the merge values of a notice as catalog-checked fields and REQ-OCC-002 by making the approved version an identifier on the document the officer signed (FSD P5 measure "notices with proof of delivery, 100 percent" is the P6 side of CTL-14).

### 4. Flow

1. Caller: generates documents for an approved treatment, or corrects the merge values of one generated draft with a reason, and so reaches API-P5-016, API-P5-017 or the one-field PATCH API-P5-006. The generation engine, the body and the content read are RWB-P5-E2026-APP's.
2. `CatalogCurrentVersionClient`: asks the catalog contract for the version in force for the template code and language on the business date, with the merge field list of that version. One hop, 2 s timeout, breaker per downstream, GET retried once with jitter (DP11).
3. `TemplateVersionBinder`: refuses when the catalog answers no Approved version (MSG-P6-005, naming template and version) or a withdrawn version (MSG-P6-003). Nothing is rendered and no row is written.
4. `MergeValueBinder`: reads every merge code of the body and of the request and compares it with the catalog list of the version in force. An unknown code refuses the whole document (MSG-P6-006, naming the code) and writes no row; a required code with no value refuses it in full (MSG-GEN-001, naming the merge code).
5. `TemplateVersionBinder`: stamps `document.template_id` with the catalog version identifier the contract returned, and writes nothing else of the version.
6. `MergeValueBinder`: writes one `document_field` row per merge value of the version, with `field_name` set to the merge code, the value, its confidence when the engine supplies one and the extractor version. A code marked `personalData` is stored and masked on read; it is never written to a log.
7. `DocumentVersionService` (API-P5-017): on a regenerate, re-reads the catalog (step 2), requires a reason, writes the next `doc_version` with `previous_version_id` set to the earlier document and `template_id` set to the version now in force; the earlier row keeps its own stamp unchanged.
8. `DocumentHubController`: answers the document or the page. No outbox row is written by this slice: the stamp and the fields travel with the `DocumentStored` event that RWB-P5-E1024-APP publishes, and that event carries identifiers and counts only.
9. A refused step writes nothing at all — no document row, no field row, no version — so a half-stamped document cannot exist.

- A refusal is a refusal of the whole document, never a partial write: the validation of steps 3 and 4 runs before the first insert, and a failed catalog read writes nothing.

### 8. Business rules

| ID | Rule | Source |
|---|---|---|
| BR1 | A document is generated or regenerated only from a template version the catalog returns as current, and a current version is Approved with its Legal approver and approval date | RWB-E1-046 BR1, BR2; REQ-OCC-002; CTL-14 |
| BR2 | Every merge value of a generated document is a code of the catalog version that stamped it, and no other field name is written by the binding | RWB-E1-046 BR4; REQ-OCC-001 |
| BR3 | The document holds the catalog version identifier only: no template attribute, no approval field and no body is copied into `rwb_document` | RWB-E1-046 BR6; DP01; ASM-3898 |
| BR4 | A regenerate writes a new document version with `previous_version_id` and a reason, and leaves the stamp of every earlier version unchanged | RWB-E1-046 BR6; API-P5-017; R-UNI-38 |
| BR5 | A document with a refused version, a refused code or a missing required value is refused in full and writes nothing | RWB-E1-046 BR5; refdata change process, step 3 |
| BR6 | A withdrawn version stops generation until Legal approves a new one, and the refusal names the template | RWB-E1-046 BR3; R-LIT-04, R-LIT-06 |
| BR7 | Templates are owned by Legal counsel as reference data, and the approval on a version is that authority | RWB-E1-046 BR7; DL28 |
| BR8 | A merge field marked `personalData` is masked by role on every read and is never written to a log, an event payload, a workflow input or a test prompt | RWB-E1-046 section 17; PDPA; DL26 |
| BR9 | The declared Documents right of the operation is enforced before any row: C to generate, U to regenerate or correct a field | TSD P5 v2 T6.1 |
| BR10 | The catalog is read as a contract, one hop with a 2 s timeout and a breaker; a failed read is a refusal and never a cached or assumed version | DP11; ADR-020 |

Where each rule lives in the target: no rule changes, and three change their mechanism. BR1, BR2, BR3 and BR6 are answered by the catalog contract: the current version, its state and its merge field list arrive in one answer, the identifier is what the document stores, and a refused answer refuses the document. BR4 is a row in `rwb_document`: the version chain is `previous_version_id` plus `doc_version`, and a regenerate never updates an earlier row. BR5 is enforced on this service's own rows: validation runs before the first insert. BR7 is an authority statement and stays with P6's approve operation. BR8 is a guardrail plus a masking call; BR9 is the guard of the service template; BR10 is the client and the fake. No template code, merge code, language or date is a constant in Java. Open decisions DL10, DL26 and DL28 stay open; the programme directive of 26 November 2026 confirms their assumptions: DL10 with ASM-2250, ASM-2357, ASM-2377 and ASM-2863; DL26 with ASM-0247, ASM-0264, ASM-0275 and ASM-0355; DL28 with ASM-1861, ASM-1925, ASM-2093 and ASM-2727.

### 9. State transitions

None for the case. This story changes no case status and no template version state; it writes the state of a document version only, on the standard record columns of TSD P5 v2 T3.0.

| From | Event | Condition | To |
|---|---|---|---|
| None | Generate (API-P5-016) | The catalog answers a current Approved version and every merge code of the body is in its list with a value | A document row with `template_id` set and its `document_field` rows written |
| None | Generate or regenerate | The version is Draft, is Withdrawn, a code is outside the catalog, a required value is missing or the catalog does not answer | No row written; the previous document and its stamp are unchanged |
| A generated version | Regenerate (API-P5-017) | A reason is given and the catalog answers a current version, which may be a later one | The next `doc_version`, with `previous_version_id` and the new `template_id` |
| A generated version | PATCH of one field (API-P5-006) | The field name is a merge code of the version stamped on that document and the caller holds Documents U | The same document version with the corrected field value and its `confirmed_by` |

The version in force can change between two generations of the same template code; that moves nothing on a document already written, and the next generation takes the version current on its own business date (BR4).

The role codes, their rights and their separation of duty stay with rwb-access (P4) and are not read here. No approval level from the delegation of authority applies to this slice: the approval is the Legal approval recorded on the catalog version.

### 13. Solution plan

**Package.** `th.co.scb.ace.workbench.recovery.document`, module `templates`. Service base `/api/recovery/document/v1`, schema `rwb_document`, topic `rwb.document.events.v1`, task queue `rwb-document` (not used by this story). Operation paths follow the Ownership Map and TSD P5 API-P5-016 (`POST /cases/{caseId}/generated-documents`); the architecture v5 slide 16 name `POST /documents/generate` is not used (ASM-101). The template version and the merge field list are read only through RWB-P6-E1046-CON, and no template row is held (ASM-102). P6 rwb-comms owns the template version, its Legal approval and the merge field catalogue; this slice supplies its own treatment values and never reads the catalogue as a table (GAP-1879).

**Components**

| Component | Type | Responsibility |
|---|---|---|
| CatalogCurrentVersionClient | Client | Calls the catalog contract for the version in force and its merge field list; one hop, 2 s timeout, breaker, GET retried once with jitter; caches for the life of the request only |
| TemplateVersionBinder | Service | Refuses a version that is not Approved or is withdrawn; stamps `document.template_id` with the catalog version identifier and copies nothing else |
| MergeValueBinder | Service | Compares every merge code of the body and the request with the list in force; refuses an unknown code or a missing required value whole; writes one `document_field` row per value |
| DocumentVersionLinker | Service | Writes the next `doc_version` with `previous_version_id` on a regenerate and requires a reason |
| TemplateBindingRepository | Repository | Reads and writes `document` and `document_field` in `rwb_document` only; no cross-schema SQL |
| TemplateBindingConfig | Configuration | Feature flag `rwb.document.template-binding`, the catalog client base URL and the timeouts |

**Database**

- No column is added: `document.template_id` (DF-DOC-032), `document.doc_version`, `document.previous_version_id` and the `document_field` columns already exist in TSD P5 v2 T3.1.
- One index, `ix_document_template` on `document` (`template_id`, `doc_version`), so the version chain of a document is one index range.
- One Flyway step, V0002, in the per-service sequence, after the V0001 baseline (DP15, H RWB-PLT-E1044-CON). The index name and the step name are Not specified in the source documents (GAP-2344; ASM-3899).
- No constraint into another schema: `template_id` carries no foreign key, because `template` is P6's table in `rwb_comms`, owned by rwb-comms (P6) and read only through RWB-P6-E1046-CON (DP01).

**Configuration and reference data**

- The catalog is data: template codes, merge codes, languages, channels, notice types, signature bases, approval users and valid-from dates are rows in `rwb_comms` and rows of the fake; none is a constant.
- The five reference lists arrive through the rwb-case reference-data contract (DP07).
- The field registry (`sys_fields`, GET /api/recovery/source-data/v1/admin/data-dictionary/fields, P1 rwb-source-data) is read as one hop with a 2 s timeout against the published data-dictionary document as a fake (DP-11); its contract dependency is Not specified in the source documents (GAP-1064).
- This slice loads no reference data: POST /admin/reference-loads is P3 rwb-case, the field-ID check sits behind the P1 data dictionary contract and the template body sits with P5 rwb-document; the load refusal rule is Not specified in the source documents (GAP-0360).
- Feature flag `rwb.document.template-binding`. Off: a generation refuses with 503 and the feature-off error of the service template, and no document is stamped (ASM-3900).

**Build steps**

1. Write the catalog client against the OpenAPI document of RWB-P6-E1046-CON and point it at the WireMock of 12.8; test the 2 s timeout, the breaker and the delayed answer (AC8).
2. Build `TemplateVersionBinder` with the Approved and Withdrawn refusals and the identifier-only stamp; test AC1, AC4 and AC5.
3. Build `MergeValueBinder`: code comparison, required-value check and one row per value; test AC2, AC3 and AC6.
4. Build `DocumentVersionLinker`: reason requirement, `previous_version_id` and the untouched earlier row; test AC7.
5. Write the migration step and the index; run the boundary test on `rwb_document` that no statement names `rwb_comms` and no key leaves the schema (AC9).
6. Wire the three components into the three operations of 12.1 behind the flag, and run the guard and guard log tests; add TC-E1-046-10 to the build.

### 17. Guardrails

- **No business value in code.** Template codes, merge codes, languages, channels, notice types, signature bases, approval users and dates are rows of the catalog or of the fake; the merge codes of the fixture appear in tests only.
- **No personal data in logs, events, workflow inputs, tests or prompts.** A merge value of a code marked `personalData` is replaced by its field name in a trace, never written to a log line, and never put in an event payload; the fixtures of sections 7 and 16 are synthetic.
- **No cross-schema read and no cross-schema key** (DP01): every statement names `rwb_document` only, `template_id` carries no foreign key into `rwb_comms`, and the catalog arrives over its contract.
- **ACE data only through the owner's contract or the `v_ace_*` views.** This module reads no ACE view and holds no grant on the recovery schema; the case is read through the case contract.
- **The stamp is an identifier only** (BR3): a template attribute, an approval field or a body copied into `rwb_document` fails the boundary test of AC9.
- **A refusal writes nothing.** The version check and the merge code check run before the first insert, and a failed catalog read writes no row and creates no version.
- **One catalog answer per request.** No version is cached beyond the request, so a version withdrawn or replaced between two calls is never reused.
- **The guard is the service template's.** This story configures the Documents right of three operations and builds no guard, no role table and no access row.
- **No event and no workflow is added.** The two service events and `DocumentIntakeWorkflow` stay with their own stories.
